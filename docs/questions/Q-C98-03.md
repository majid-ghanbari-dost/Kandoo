# Q-C98-03 — the invoices list has no data source

**Filed:** 2026-11-25 · **Lane:** C# · **Stage:** T3 stage 4 (C-96 group 2) · **Blocks:** `Invoices.dc.html` screen

## The gap

`Invoices.dc.html` specifies a list with filter chips (`همه`, `پیامک ارسال شد`, `نیازمند بازبینی`, `لغوشده`) and columns `شماره` / `مشتری` / `تاریخ` / `مبلغ` / `وضعیت`.

**The Hub has no read route for invoices.** Its invoice API is write-only:

| Route | Method |
|---|---|
| `/v1/stores/{id}/invoices/drafts` | POST |
| `/v1/stores/{id}/invoices/{invoice_id}/items` | POST |
| `/v1/stores/{id}/invoices/{invoice_id}/issue` | POST |
| `/v1/stores/{id}/invoices/{invoice_id}/sms/resend` | POST |

Verified by grep over `src/Kandoo.Hub/`: no `MapGet` for invoices. Products, by contrast, do have `GET /v1/stores/{id}/products` with search, limit and cursor — so the pattern exists to copy.

The app's `InvoicesListPage` has a "بارگذاری فاکتورها" button with nothing to call.

## Why the lane did not add it here

Adding a read route means deciding, before writing code:

1. **Which projection** — the same `InvoiceProjection` as issue, or a lighter list projection (the board wants five columns, not the items array)?
2. **Whether filters are query parameters or client-side.** `sms sent` is not a field on the invoice aggregate; it lives in the SMS delivery record. `needs review` is a Mode B review state. `cancelled` maps to `retirement_reason`. One of the four filters has no column behind it today.
3. **Pagination contract** — products use `limit` + `next_cursor`; matching that is the obvious default, but it fixes the shape of a public route.

Those are architecture decisions of the same weight as the accounting routes, which went through their own task. Doing them inline, inside a screen-verification stage, is how a read API ends up shaped by whichever screen needed it first.

## Options

| # | Option | Consequence |
|---|---|---|
| **A** | Dedicated task: `GET /v1/stores/{id}/invoices` with `limit`/`cursor`, list projection, and the filters that have real columns; `sms sent` and `needs review` added as their own fields in a follow-up | Clean contract; the screen can then be built once and correctly. **Recommended.** |
| **B** | Ship the list from the **replication log** (`replication_log` already holds every `invoice.issue` with payload) | No new write path, but the read becomes an audit-log query, and drafts (never issued) would not appear — the board shows drafts too |
| **C** | Build the screen against an app-side cache of invoices the app itself created this session | Zero server work, but the list is empty after a restart — not what the board sells |
| **D** | Drop the list from the demo and say so | Cheapest; the PO cannot show "all my invoices" |

## Recommendation

**A**, scheduled as its own item (it is server work plus tests, roughly a day).

Interim: the screen keeps its explicit empty state and the report says the list is `PARTIAL — no data source`, rather than a button that fails silently when pressed.

## One-line answer needed

**A, B, C, or D.**
