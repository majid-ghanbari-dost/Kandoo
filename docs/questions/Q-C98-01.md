# Q-C98-01 — who owns the customer invoice link in the offline demo?

**Filed:** 2026-11-25 · **Lane:** C# · **Stage:** C-98 (STAGE 2) · **Blocks:** DoD-A point 3 (last two steps)

## What is missing

The demo chain is:

> install → first-run setup → create a product → issue an invoice (Mode A) → **the SMS line appears in the local outbox** → **the customer web invoice page opens from the outbox link on the PO's phone over the LAN**

Steps up to and including the SMS line are now green in CI (`C98_POINT=7 PASS(sms-outbox)`). The last step is not:

- the public invoice page `/i/{token}` is served **only by `Kandoo.Cloud`** (`src/Kandoo.Cloud/Program.cs:35`). It renders `PublicInvoiceHtml` and is gated on the token being in the Cloud's `public_invoices` table;
- the **Hub has no such route**. Its only non-API pages are `/` and `/pairing-grant`, both loopback-only;
- when the Hub issues an invoice it produces **no customer link at all**, so the outbox line that the demo SMS writes contains no URL. Hence `C98_POINT=8 GAP(customer-link) the outbox line carries no http(s) link`.

## Why the C# lane did not just build it

Doing so would mean either:

1. **Serving `/i/{token}` from the Hub** — a second implementation of a page that is deliberately a Cloud/PHP-lane responsibility (P-36), rendering the same board `Customer-Invoice-v2.dc.html` from two codebases; or
2. **Making the Hub mint a Cloud token at issue time** — but the demo runs with **no internet**, and the Cloud may not even be running on the PO's PC.

Both are architecture decisions, not lane decisions. The sprint rule is explicit that out-of-scope items go to a Q file rather than being invented.

## Options

| # | Option | Consequence |
|---|---|---|
| **A** | The **PHP/Cloud lane** runs the local Cloud on the PO's PC and the Hub replicates the issued invoice to it; the outbox link points at `http://<LAN-IP>:<cloud-port>/i/<token>` | Keeps one implementation of the customer page. Adds "local Cloud must be running" to the demo, and needs Hub→Cloud replication to work offline over the LAN. |
| **B** | The **C# lane** serves a Hub-side `/i/{token}` page for the demo profile only (`Hub:Demo:Mode`) | Demo works with the Hub alone. Costs a second renderer of the same board; risk of divergence from P-36. |
| **C** | The **C# lane** writes the link into the outbox as a **file path** to a locally exported HTML/PDF of the issued invoice (no web server) | Simplest, fully offline, no new route. The "page on the phone over the LAN" requirement becomes "open the file on the PC and show it" — a real reduction in the demo. |
| **D** | Drop the customer-page step from the DoD-A demo and say so to the PO | Most honest, least work; loses a headline demo step. |

## Recommendation

**Option A**, with **Option C as the fallback** if local Cloud cannot be up on the PO's PC in time.

Reason: the customer page is a real product surface with its own board and its own lane; duplicating it in the Hub (B) is the one option that creates permanent maintenance debt, and the PO's own demo script already assumes the Cloud is part of the local kit.

Whichever is chosen, `scripts/demo-check.ps1` needs no change to detect it: point 8 already looks for an `http(s)` link in the outbox line and will flip to `PASS` the moment one is there. If Option C is chosen instead, the link check should be replaced by an "exported file exists" check — a one-line change in that point.

## What the lane needs to continue

A one-line answer: **A, B, C, or D**. Until then Stage 3 proceeds in parallel — this blocks only the last demo step, not the C-96 screen verification chain.
