# C-41 — Android pairing and Windows owner device administration

**Scope:** extend the C-40 MAUI screen with Android QR-JSON pairing-code entry and Windows owner device list/level/revoke, using the existing C-08/C-25/C-36 Hub APIs. MAUI, the C-40 token dictionary, local Vazirmatn fonts, REAL/FAKE review behavior, and the external app test project remain in use. `Kandoo.sln` and `.github/workflows/ci.yml` remain untouched.

## Delivered behavior

- In REAL mode on Android, the pairing section accepts the existing single-use companion QR JSON (`protocol_version=0`), validates its non-loopback HTTPS Hub endpoint, and calls unauthenticated `POST /v1/pairing-grants/consume` with a new device GUID, user-entered label, `platform=ANDROID`, and a generated RSA public key. The request never sends `operator_level` or `requested_level`; the owner-issued grant remains authoritative. Success fills the in-memory Hub URL/store/session fields and clears the entered QR code. Session tokens and device credentials are never rendered or logged.
- In REAL mode on Windows, the Devices section calls bearer-authenticated `GET /v1/stores/{store_id}/devices`, `PATCH /v1/stores/{store_id}/devices/{device_id}/level`, and `POST /v1/stores/{store_id}/devices/{device_id}/revoke`. The UI exposes `SELLER`, `OPERATOR`, and `MANAGER` only for active companion rows; Hub and revoked rows cannot be administered. Level changes and confirmed revocations reload the authoritative list.
- All new visual values reference the same merged `DesignTokens.xaml`, including 48dp minimum targets, palette, fonts, spacing, and RTL styles. No second token source was added.
- App logic tests cover QR validation, exact consume payloads without phone level override, pairing response mapping, device list/level/revoke routes and bearer auth, admin eligibility, and owner-error refusal.

## Boundaries

- Pairing is paste-entry, not camera scanning. Credentials and pairing state are in-memory only; no secure persistent credential store or restart/resume flow is claimed. A newly generated public/private key pair is not persisted.
- FAKE mode remains limited to the clearly bannered review demo. Pairing and device administration are REAL-only and have no fake mutations.
- Local review is static only; CI is the .NET build/test executor. Build success is not device rendering, Persian-shaping, touch, owner-session, or device/UI automation evidence. The Product Owner device gate remains pending.
