# C-25 — Hub access and session role enforcement

## Contract-led audit

The review is limited to existing authority: `docs/domain-model.md` §2.4 requires exactly one active `HUB`, forbids companion write authority, and says device attribution does not replace membership; `docs/sync-protocol.md` §3.7 and `docs/cloud-api-contract.md` define `HUB_ALREADY_ACTIVE` and restore-only writer replacement. C-08 already forbids HUB-role pairing grants and unpaired writes. No new `OPERATOR`/`CUSTOMER` membership or permission model is inferred or implemented.

| Checked path | Existing behavior / C-25 result |
| --- | --- |
| Pairing-grant issue, device list, companion revoke | Authenticated owner session was already required; regression coverage now proves a companion receives `OWNER_REQUIRED`. |
| Pairing consume / session resume | Companion-only grant, credential, expiry, replay and revocation behavior remains unchanged. |
| Owner bootstrap | **Gap:** an existing device was ignored by `ON CONFLICT DO NOTHING`, yet a new HUB/owner session was issued. This permitted companion promotion and owner rebinding when bootstrap was configured; a second Hub could also be inserted. |
| Session authentication | **Gap:** persisted session role/owner were trusted without comparison with the current paired device. |

## Minimal enforcement and evidence

- `IssueOwnerSession` now atomically accepts only initial Hub creation or renewal for the identical active `(store, Hub device, owner)` binding. Existing companion/cross-store/owner mismatches roll back with public `OWNER_BOOTSTRAP_INVALID`; another active Hub returns the already-contracted `HUB_ALREADY_ACTIVE`. No token or hidden session is created on denial.
- Authentication now fails closed with `SESSION_INVALID` if session role/owner drift from the paired device. Owner-only endpoint behavior, companion operations, restore flows and all frozen API schemas are otherwise unchanged.
- Three C-25 API/store tests cover companion elevation plus owner-only routes, second-Hub/owner-rebind/cross-store denial with valid same-Hub renewal, and persisted role drift. Session counts and device state verify no partial effects.
- Boundary: this is Hub-local role hardening, not a membership administration feature, ownership-transfer workflow, Cloud implementation change, UI change, or authorization to replace a Hub outside restore.

No local .NET execution is claimed. Static review and `git diff --check` are local; compile and all tests require observed CI. New CI cells remain pending executive verification.
