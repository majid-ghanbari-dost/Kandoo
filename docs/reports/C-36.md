# C-36 — Owner-chosen companion device levels

**Scope:** additive reuse of the C-08/C-25 pairing, session, device-list, and revocation paths. `SELLER`, `OPERATOR`, and `MANAGER` are companion operator levels, not `HUB` roles, owner identities, or a new permission model. Existing owner-only device administration remains unchanged. No frozen contract or canonical restore state was edited.

## Delivered behavior

- The owner pairing-grant request accepts optional `requested_level`. New QR payloads expose the selected `operator_level`, retain `device_role=COMPANION`, remain single-use, and expire after the existing five minutes. Android/phone redemption uses the existing consume endpoint and receives only the level stored on the owner-issued grant; phone-supplied `operator_level` or `requested_level` fields cannot override it. Omitted `requested_level` and legacy unconsumed grants with a null level default to `OPERATOR` for compatibility.
- Nullable `operator_level` columns are added to `devices` and `pairing_grants` through the existing additive SQLite migration path. Existing device rows are not backfilled or rewritten. Device list and pairing responses expose the level; the Hub device has no operator level.
- Owner-only `PATCH /v1/stores/{store_id}/devices/{device_id}/level` changes an active companion to one of the three supported levels and records `DEVICE_LEVEL_CHANGED` through the existing access-audit mechanism. A companion, including one already at `MANAGER`, cannot change its own or another device's level. Hub targets, unsupported levels, and revoked targets are rejected. Existing revocation still invalidates authentication/session resume and retains the last level in the device list.
- The real PATCH route is included in generated `/openapi/v1.json` and the expected-path contract test; frozen `docs/openapi.yaml` is unchanged.
